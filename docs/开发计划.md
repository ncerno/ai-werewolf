## Phase 1: 项目骨架

### 目标
搭好目录结构、依赖管理、配置框架，确保项目可跑。

### 任务
1. 创建完整目录结构
2. `requirements.txt`：fastapi, uvicorn, openai, python-dotenv, websockets, pyyaml
3. `config/default.yaml`：默认游戏参数、LLM 配置模板
4. `src/utils/config.py`：配置加载器（读 yaml + 环境变量覆盖）
5. `src/utils/logger.py`：日志系统（控制台彩色 + 文件写入）
6. `src/main.py`：FastAPI 启动入口（空壳，先能启动）
7. 验证：`python src/main.py` 启动成功，访问 `http://localhost:8000`

---

## Phase 2: 游戏规则引擎

### 目标
实现纯逻辑的游戏状态管理和规则判定，完全与 LLM 无关，可独立测试。

### 任务
1. **`src/engine/state.py`** — GameState 数据结构
   - 玩家列表（id, role, alive, has_vote, 技能使用状态）
   - 游戏阶段枚举（NIGHT_WOLF, NIGHT_WITCH, NIGHT_SEER, NIGHT_HUNTER, DAY_ELECTION, DAY_SPEECH, DAY_VOTE, GAME_OVER）
   - 回合计数、警长 ID、狼刀目标、女巫用药记录
2. **`src/engine/rules.py`** — RuleEngine 纯函数
   - `check_winner(state)` → 胜利判定（屠边 + 狼数>=好人数）
   - `validate_action(state, player_id, action)` → 行动合法性
   - `tally_votes(votes)` → 计票 + 平票处理
   - `get_night_order(state)` → 夜晚唤醒顺序
3. **`src/engine/controller.py`** — GameController 调度器
   - 回合推进：夜晚 → 白天 → 夜晚循环
   - 阶段切换、并发控制
   - 事件回调（供 WebSocket 推送）
4. **`tests/test_engine.py`** — 规则引擎单元测试
   - 覆盖各种胜利条件、边界情况、非法行动拦截
5. 验证：`python -m pytest tests/test_engine.py -v` 全部通过

## Phase 3: LLM Agent 层

### 目标
封装 LLM 调用、Prompt 构建、行动解析，每个 Agent 独立运行。

### 任务
1. **`src/agent/prompts.py`** — 角色 Prompt 模板
   - 狼人 prompt：知道同伴、不知道神职
   - 预言家 prompt：知道查验结果
   - 女巫 prompt：知道用药状态
   - 猎人 prompt：知道开枪状态
   - 白痴/平民 prompt：只知道公共信息
   - 所有 prompt 强制要求 `【行动】ACTION ID` 格式
   - 格式示例和使用说明
2. **`src/agent/player.py`** — PlayerAgent 类
   - LLM 调用封装（openai 库，兼容多 provider）
   - `observe(event)` 追加记忆
   - `decide(action_hint)` 异步决策
   - `summarize()` 自我总结压缩记忆
3. **`src/agent/parser.py`** — ActionParser
   - 正则提取 `【行动】ACTION ID`
   - 模糊匹配（容错大小写、空格）
   - 合法性代理 → 无效时重试 → 随机兜底
4. **`src/agent/god_agent.py`** — GodAgent（模式三用）
   - 上帝 AI 的系统 prompt
   - 裁判话术生成
5. **`tests/test_parser.py`** — Parser 单元测试
   - 正常输入、格式错误、非法目标、空白输出
6. 验证：`python -m pytest tests/test_parser.py -v`

## Phase 4: FastAPI 后端

### 目标
提供 REST API + WebSocket，连接前端和游戏引擎。

### 任务
1. **`src/server/app.py`** — FastAPI 应用
   - REST 端点：创建游戏、获取状态、提交行动
   - WebSocket 端点：游戏事件实时推送
2. **`src/server/game_manager.py`** — 游戏实例管理
   - 多游戏 session 隔离
   - 模式切换（旁观/上帝/玩家）
3. **`src/server/ws_handler.py`** — WebSocket 消息协议
   - 消息类型定义（game_state, public_log, private_log, action_request）
   - 用户认证（简单 token 或 session）
4. 验证：启动服务后用 WebSocket 客户端测试连接

## Phase 5: Web 前端

### 目标
三个页面：主页、设置页、游戏页。部署到域名后可任何设备访问。

### 任务
1. **主页**
   - 模式选择卡片（旁观/上帝/玩家）
   - 进入游戏按钮
2. **设置页**
   - 模型配置表单（默认模型、按角色覆盖模型）
   - API Key、API Base URL
   - Temperature、发言时间上限等参数
   - 保存到 `data/user_config.json`
3. **游戏页**
   - 主日志流（左侧/中央）：发言内容、行动结果、系统消息
     - 角色颜色区分（狼人红、神职蓝、平民绿、系统白）
     - 实时滚动，新消息自动出现
   - 私密信息面板（右侧，模式三专用）：
     - 身份牌显示
     - 狼队友列表（如果你是狼）
     - 上帝反馈（查验结果、用药提示、行动状态）
   - 输入区（底部）：
     - 模式二：上帝指令按钮（推进阶段、确认死讯、宣布投票等）
     - 模式三：文本输入框（自然语言发言）+ 投票面板
   - 状态栏（顶部）：回合数、当前阶段、存活人数、倒计时
4. **WebSocket 客户端**
   - 连接管理、断线重连
   - 消息分发（公开/私密）
5. 验证：浏览器打开，三页面可切换，WebSocket 连接成功

## Phase 6: 三种模式串联

### 目标
将引擎、Agent、后端、前端串联成完整游戏流程。

### 任务
1. **旁观模式** — 全自动
   - 点击开始 → 游戏自动运行至结束
   - 所有 AI 决策实时推送到前端日志
   - 无人工干预
2. **上帝模式** — 用户控制节奏
   - 用户通过按钮推进每个阶段
   - 用户查看 AI 决策后手动确认/驳回
   - 用户宣布死讯、投票结果
   - 引擎提供可选行动列表，用户选择后执行
3. **玩家模式** — 用户参与
   - 随机分配身份 → 私密窗口显示身份信息
   - AI 上帝主持流程
   - 轮到用户发言时输入框激活
   - 投票时显示投票面板
   - 夜晚阶段私密窗口显示相关信息
4. 验证：三种模式分别完整跑通一局游戏

## Phase 7: 部署与打磨

### 目标
部署到域名，错误处理完善，体验优化。

### 任务
1. **错误处理**
   - LLM 调用超时重试
   - 网络断开后的状态恢复
   - 配置错误的前端提示
2. **日志持久化**
   - 游戏日志自动保存到 `data/game_logs/`
   - 支持回放查看
3. **部署**
   - Nginx 反向代理配置
   - systemd 服务或 Docker 容器
   - 域名绑定
4. **最终验证**
   - 手机浏览器访问域名 → 完整游戏体验
   - LLM 响应延迟在可接受范围（单次决策 < 5 秒）

## 技术决策记录

| 决策 | 选择 | 理由 |
|------|------|------|
| 后端框架 | FastAPI | 原生 async + WebSocket，比 Flask 更适合 |
| 前端 | 原生 HTML/JS | 无需额外框架学习成本，部署简单 |
| 实时推送 | WebSocket | HTTP 轮询延迟太高，不适合实时游戏 |
| 规则引擎 | 硬编码 | 可靠性要求极高，LLM 做裁判不可靠 |
| 配置格式 | YAML + JSON | YAML 默认配置可读性好，JSON 用户配置兼容前端 |
| God Agent | 模式三用 LLM | 生成自然语言话术，硬编码做裁判逻辑 |
